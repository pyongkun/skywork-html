제1부: Git의 정신 모델

1. Git은 무엇인가

Git은 파일을 클라우드에 올리는 프로그램이 아니라, 프로젝트의 변경 역사를 로컬에서 기록하고 연결해 관리하는 분산 버전 관리 시스템입니다.

“버전 관리”가 필요한 이유를 문서 편집에 비유해 봅시다.

보고서_최종.docx
보고서_진짜최종.docx
보고서_진짜최종_수정.docx
보고서_제출용_최종2.docx

이 방식은 어느 파일이 기준인지, 무엇이 달라졌는지, 누가 왜 바꿨는지 알기 어렵습니다. Git은 각 시점의 프로젝트 상태를 커밋으로 기록하고, 커밋에 설명과 작성자, 이전 커밋과의 관계를 붙입니다.

Git의 핵심 가치는 다음과 같습니다.

  • 시간 여행: 이전 상태를 조사하고 필요한 변경을 복원한다.
  • 실험의 격리: 브랜치에서 안전하게 기능을 만든다.
  • 협업: 여러 개발자의 변경을 비교하고 통합한다.
  • 책임 추적: 누가, 언제, 왜 변경했는지 기록한다.
  • 자동화의 기준점: 특정 커밋을 빌드·테스트·배포한다.

Git은 “자동 저장”이 아닙니다. 사용자가 무엇을 하나의 의미 있는 단위로 기록할지 선택해야 합니다. 그래서 좋은 Git 사용은 명령어 기술보다 변경을 의미 있는 단위로 나누는 사고방식에 가깝습니다.

2. Git과 GitHub는 어떻게 다른가

Git과 GitHub를 혼동하면 원격 작업이 어렵게 느껴집니다.

  • Git: 내 컴퓨터에서 저장소와 커밋을 관리하는 도구이자 규칙
  • GitHub: Git 저장소를 인터넷에서 호스팅하고 Pull Request, 이슈, 코드 리뷰, 권한, Actions 등을 제공하는 서비스
  • GitLab, Bitbucket, Azure DevOps: GitHub와 비슷한 역할을 하는 다른 호스팅 서비스

인터넷 연결 없이도 다음 작업은 가능합니다.

git init
git add .
git commit -m "초기 버전"
git branch feature/login
git log

반면 push, fetch, 호스팅 서비스의 Pull Request는 원격 서버와 관련됩니다.

중요한 구분은 이것입니다.

Git 저장소 = 커밋과 브랜치 역사를 저장하는 구조
GitHub 저장소 = 그 Git 저장소를 서버에서 제공하는 사본 + 협업 기능
Pull Request = Git 명령이 아니라 호스팅 서비스의 리뷰 절차

3. 스냅샷, 객체, 커밋 그래프

3.1 Git은 “차이만 저장하는 폴더”라고만 보면 부족하다

개념적으로 Git은 커밋할 때 프로젝트의 스냅샷을 기록합니다. 변경되지 않은 파일은 기존 객체를 재사용하므로 매번 모든 파일을 물리적으로 복제하는 것은 아닙니다.

커밋에는 대략 다음 정보가 연결됩니다.

  • 프로젝트 파일 트리
  • 작성자와 커미터
  • 시각
  • 커밋 메시지
  • 부모 커밋

따라서 커밋은 단순 번호가 아니라, 이전 커밋을 가리키는 노드입니다.

A---B---C

여기서 C는 B를 부모로, B는 A를 부모로 가집니다. 브랜치가 갈라지면 그래프가 됩니다.

A---B---C  main
     \
      D---E  feature

3.2 커밋 해시는 내용 기반 식별자다

커밋은 a1b2c3d... 같은 해시로 식별됩니다. 보통 짧은 앞부분만 사용해도 저장소 안에서 구분됩니다.

git show a1b2c3d

해시는 “몇 번째 버전” 같은 순번이 아닙니다. 커밋 내용과 메타데이터, 부모 관계가 달라지면 해시도 달라집니다. 그래서 rebase나 amend로 커밋을 다시 만들면 겉보기 파일 내용이 비슷해도 새 해시가 생깁니다.

4. 작업 디렉터리·스테이징 영역·저장소

Git 초보자가 가장 먼저 이해해야 할 모델입니다.

작업 디렉터리  -- git add -->  스테이징 영역  -- git commit -->  로컬 저장소
   현재 편집본                   다음 커밋 후보                    기록된 역사

4.1 작업 디렉터리

에디터로 실제 파일을 수정하는 공간입니다. 아직 커밋하지 않은 변경이 존재할 수 있습니다.

4.2 스테이징 영역

다음 커밋에 포함할 정확한 변경 집합을 준비하는 공간입니다. 흔히 index라고도 부릅니다.

스테이징은 번거로운 중간 단계가 아니라, 변경을 편집하는 기능입니다. 한 파일에 버그 수정과 문구 변경이 함께 있어도 git add -p로 일부만 선택할 수 있습니다.

4.3 로컬 저장소

.git 디렉터리에 커밋, 브랜치, 태그, 설정 등이 기록됩니다. 보통 .git을 직접 편집하지 않습니다.

4.4 세 가지 비교

git diff            # 작업 디렉터리와 스테이징 영역의 차이
git diff --staged   # 스테이징 영역과 HEAD 커밋의 차이
git diff HEAD       # 작업 디렉터리 전체와 HEAD 커밋의 차이

실습: 일부만 커밋하기

mkdir git-lab
cd git-lab
git init --initial-branch=main
printf "# 할 일\n" > todo.md
git add todo.md
git commit -m "docs: 할 일 문서 시작"

printf "- 로그인 구현\n" >> todo.md
printf "임시 메모\n" > scratch.txt

git status
git add todo.md
git diff
git diff --staged
git commit -m "docs: 로그인 작업 추가"

여기서 scratch.txt는 작업 디렉터리에는 있지만 스테이징하지 않았으므로 커밋에 들어가지 않습니다.

5. HEAD, 브랜치, 태그라는 이름표

커밋 해시는 기억하기 어렵습니다. Git은 커밋에 의미 있는 이름을 붙이는 참조를 제공합니다.

5.1 브랜치는 움직이는 포인터

브랜치를 “프로젝트 폴더 복사본”이라고 생각하면 곧 한계가 옵니다. 브랜치는 특정 커밋을 가리키는 가벼운 이름표입니다. 그 브랜치에서 커밋하면 이름표가 새 커밋으로 이동합니다.

A---B---C  main

main에서 새 커밋 D를 만들면:

A---B---C---D  main

5.2 HEAD는 내가 현재 보고 있는 위치

보통 HEAD는 현재 브랜치를 가리킵니다.

HEAD -> main -> D

git switch feature를 하면 HEAD가 feature를 가리킵니다. 특정 커밋을 직접 checkout하면 HEAD가 브랜치가 아닌 커밋을 가리키며 detached HEAD 상태가 됩니다.

5.3 태그는 보통 움직이지 않는 이름표

v1.0.0처럼 배포 지점을 표시할 때 태그를 사용합니다. 브랜치는 개발하면서 움직이고, 태그는 특정 릴리스를 고정해 가리키는 것이 일반적입니다.

6. 설치 확인과 최초 설정

git --version
git config --global user.name "홍길동"
git config --global user.email "hong@example.com"
git config --global init.defaultBranch main
git config --global --list

이 이름과 이메일은 로그인 계정이 아니라 커밋 메타데이터입니다. 회사와 개인 프로젝트에서 다른 이메일이 필요하다면 저장소 안에서 로컬 설정을 덮어쓸 수 있습니다.

git config user.email "hong@company.example"

설정 범위는 대략 다음 순서로 이해하면 됩니다.

system < global < local

더 가까운 범위의 설정이 우선합니다.

7. 첫 저장소 만들기

7.1 새 프로젝트 시작

mkdir hello-git
cd hello-git
git init --initial-branch=main
printf "console.log('Hello Git');\n" > app.js
git status
git add app.js
git commit -m "feat: 첫 인사 프로그램 추가"

git init은 현재 폴더를 Git 저장소로 바꿉니다. 파일을 서버에 올리지 않으며, 자동으로 커밋하지도 않습니다.

7.2 기존 저장소 복제

git clone https://example.com/team/sample.git
cd sample

clone은 보통 다음을 함께 수행합니다.

  • 원격 저장소의 커밋과 참조를 내려받는다.
  • 작업 디렉터리를 만든다.
  • 원격 이름 origin을 설정한다.
  • 기본 브랜치를 checkout한다.

8. 변경 관찰, 선택, 커밋

일상 작업의 가장 안전한 리듬은 다음과 같습니다.

git status
git diff
git add -p
git diff --staged
git commit -m "fix: 빈 사용자 이름 검증"

8.1 git status는 나침반이다

문제가 생기면 먼저 git status를 봅니다. 현재 브랜치, 변경 파일, 충돌 상태, rebase 진행 여부, 다음 행동 힌트를 보여줍니다.

8.2 git add는 저장이 아니라 선택이다

git add .는 편하지만 무관한 파일이나 비밀정보까지 넣을 수 있습니다. 초보 단계에서는 파일별 또는 패치별 추가를 권합니다.

git add src/login.js
git add -p

패치 모드에서 자주 보는 선택:

  • y: 이 조각을 스테이징
  • n: 이 조각은 제외
  • s: 더 작은 조각으로 나누기
  • q: 종료

8.3 좋은 커밋은 한 문장으로 설명 가능하다

좋은 커밋은 작고 논리적으로 완결되어야 합니다.

나쁜 예:

수정
작업함
여러 가지 변경

좋은 예:

feat: 비밀번호 재설정 폼 추가
fix: 만료된 토큰이 승인되는 오류 수정
test: 로그인 실패 시나리오 추가
refactor: 인증 검증 로직을 서비스로 분리

커밋 메시지는 “무엇을 타이핑했는가”보다 왜 이 변경이 필요한가를 후대의 독자에게 설명해야 합니다.

8.4 실습: 한 파일의 두 의도를 나누기

app.js에 기능 변경과 디버그 로그 제거를 함께 만들었다고 가정합니다.

git diff
git add -p app.js
# 기능 변경 조각만 y
git diff --staged
git commit -m "feat: 사용자 환영 메시지 추가"

git add -p app.js
# 로그 제거 조각을 y
git commit -m "chore: 임시 디버그 로그 제거"

이렇게 하면 리뷰와 되돌리기가 쉬워집니다.

9. 이력 읽기와 비교하기

Git을 잘 쓰는 사람은 기록만큼 관찰을 많이 합니다.

git log --oneline --graph --decorate --all
git show HEAD
git show HEAD~1
git log -- app.js
git log --follow -- old-name.js
git diff main..feature/login
git diff main...feature/login

HEAD~1은 첫 번째 부모를 한 단계 거슬러 올라간 커밋입니다. main...feature의 세 점 비교는 두 브랜치의 공통 조상 이후 feature 쪽 변경을 보는 데 유용합니다.

실습 질문

다음 그래프에서 feature 브랜치가 추가한 변경만 보고 싶다면 무엇을 기준으로 비교해야 할까요?

A---B---C---D  main
     \
      E---F  feature

핵심은 최신 커밋 C나 D가 아니라 공통 조상 B입니다. 세 점 비교는 이 의도를 표현합니다.

git diff main...feature

10. 무시 파일과 비밀정보

.gitignore는 Git이 아직 추적하지 않는 파일을 기본 후보에서 제외합니다.

# 의존성
node_modules/
venv/

# 빌드 결과
dist/
build/

# 환경·비밀정보
.env
.env.*
!.env.example

# 운영체제와 편집기
.DS_Store
Thumbs.db
.idea/
*.swp

이미 추적 중인 파일은 .gitignore에 넣어도 자동으로 사라지지 않습니다.

git rm --cached .env
git commit -m "chore: 환경 파일 추적 중지"

보안 경고: 비밀키를 커밋했다면 파일을 삭제하는 것만으로 충분하지 않습니다. 과거 커밋에 남아 있을 수 있으므로 먼저 해당 키를 즉시 폐기·재발급해야 합니다. 이력 제거는 팀 전체에 영향을 주는 별도의 고위험 작업입니다.

제3부: 브랜치와 원격 협업

11. 브랜치의 개념

브랜치는 독립적인 실험 흐름을 만드는 이름표입니다.

git switch -c feature/profile
# 파일 수정
git add .
git commit -m "feat: 프로필 화면 골격 추가"
git switch main

이때 feature의 파일이 사라진 것이 아니라, HEAD가 main을 가리키며 작업 디렉터리가 main의 스냅샷으로 바뀐 것입니다.

브랜치 이름 예

feature/password-reset
fix/login-timeout
refactor/user-service
hotfix/payment-duplicate

한 브랜치는 가능한 한 하나의 목적을 가져야 합니다. 오래 살아 있는 브랜치는 main과 차이가 커져 통합 비용이 증가합니다.

12. 병합과 충돌

12.1 fast-forward 병합

main이 분기 후 움직이지 않았다면 포인터만 앞으로 이동할 수 있습니다.

A---B  main
     \
      C---D  feature

병합 후:

A---B---C---D  main, feature

git switch main
git merge feature

12.2 merge commit

양쪽이 모두 진행되었다면 두 부모를 가진 병합 커밋이 생길 수 있습니다.

A---B---C-------M  main
     \         /
      D---E---F    feature

병합은 “두 역사가 실제로 갈라졌다가 합쳐졌다”는 사실을 보존합니다.

12.3 충돌은 실패가 아니라 판단 요청이다

Git이 두 변경을 자동으로 합칠 근거가 없으면 사람에게 의도를 묻습니다.

<<<<<<< HEAD
const timeout = 3000;
=======
const timeout = 5000;
>>>>>>> feature/network
  • HEAD 쪽: 현재 브랜치의 내용
  • 구분선 아래: 가져오는 브랜치의 내용
  • 해결은 둘 중 하나를 고르는 것일 수도, 두 의도를 조합하는 것일 수도 있음

안전한 절차:

git status
# 파일을 열어 충돌 표식을 제거하고 올바른 최종 내용을 작성
git diff
git add src/config.js
git status
git merge --continue

판단이 어렵다면:

git merge --abort

충돌 실습

git init --initial-branch=main conflict-lab
cd conflict-lab
printf "색상=파랑\n" > config.txt
git add .
git commit -m "chore: 기본 색상 설정"

git switch -c feature/red
printf "색상=빨강\n" > config.txt
git commit -am "feat: 빨간 테마 적용"

git switch main
printf "색상=초록\n" > config.txt
git commit -am "feat: 초록 테마 적용"

git merge feature/red
# 충돌 내용을 확인하고 팀의 의도에 맞게 수정
git add config.txt
git commit

중요한 질문은 “ours와 theirs 중 무엇이 최신인가?”가 아니라 “최종 제품에서 어떤 의미가 맞는가?”입니다.

13. 원격 저장소의 정신 모델

원격 저장소는 내 저장소의 실시간 거울이 아닙니다. 로컬 저장소와 원격 저장소는 독립된 커밋 그래프를 갖고 명시적으로 동기화합니다.

로컬 브랜치 main
원격 추적 브랜치 origin/main
원격 서버의 실제 main

origin은 관례적인 원격 이름일 뿐 특별한 예약어가 아닙니다. origin/main은 “마지막으로 fetch했을 때 알고 있던 origin의 main”을 나타내는 로컬 참조입니다.

git remote -v
git remote add origin https://example.com/team/app.git
git remote show origin

HTTPS URL과 SSH URL은 전송·인증 방식이 다르지만 같은 저장소를 가리킬 수 있습니다.

https://host/team/app.git
git@host:team/app.git

14. clone, fetch, pull, push

14.1 fetch: 소식을 가져오되 내 작업은 합치지 않는다

git fetch origin
git log --oneline main..origin/main
git diff main...origin/main

fetch는 원격 커밋을 내려받고 원격 추적 브랜치를 갱신하지만 현재 브랜치를 자동으로 병합하지 않습니다. 그래서 관찰하기 좋은 안전한 기본 동작입니다.

14.2 pull: 가져온 뒤 통합한다

개념적으로 보통 다음 조합입니다.

git pull = git fetch + merge 또는 rebase

git pull --ff-only
git pull --rebase

초보자는 자동 통합이 당황스러울 수 있으므로 fetch 후 차이를 보고 직접 merge/rebase하는 흐름이 이해에 도움이 됩니다.

14.3 push: 로컬 참조를 원격에 제안한다

git push -u origin feature/profile

-u는 로컬 브랜치와 원격 브랜치의 upstream 관계를 설정합니다. 이후에는 git push, git pull을 간단히 쓸 수 있습니다.

push가 거절되는 흔한 이유는 원격 브랜치에 내 로컬에 없는 커밋이 있기 때문입니다. 이것은 Git이 다른 사람의 역사를 실수로 덮어쓰지 않게 보호하는 동작입니다.

15. GitHub Flow 중심 협업

작은 팀에 이해하기 쉬운 흐름입니다.

  1. main을 최신으로 만든다.
  2. 짧은 기능 브랜치를 만든다.
  3. 작은 커밋으로 구현한다.
  4. 원격에 push한다.
  5. Pull Request를 열어 리뷰와 자동 테스트를 받는다.
  6. 승인 후 merge한다.
  7. 로컬과 원격의 작업 브랜치를 정리한다.
git switch main
git fetch origin
git merge --ff-only origin/main
git switch -c feature/avatar-upload

# 구현과 테스트
git add -p
git commit -m "feat: 아바타 업로드 검증 추가"
git push -u origin feature/avatar-upload

Pull Request는 단순히 “merge 버튼”이 아닙니다. 변경 의도, 범위, 테스트 방법, 위험요소를 공유하는 협업 문서입니다.

좋은 PR 설명 예:

목적: 프로필 사진 업로드 시 잘못된 파일 형식을 조기에 거부한다.
변경: MIME 형식과 크기 검증을 추가했다.
검증: jpg/png 정상 업로드, gif 거부, 용량 초과 거부를 테스트했다.
주의: 실제 이미지 변환은 다음 PR 범위다.

16. Fork와 Pull Request

원본 저장소에 직접 push 권한이 없을 때 자신의 계정으로 fork한 뒤 변경을 제안할 수 있습니다.

관례:

origin   = 내 fork
upstream = 원본 저장소

git clone git@host:me/project.git
cd project
git remote add upstream git@host:team/project.git
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

Git 자체는 fork나 PR을 특별히 알지 못합니다. Git 관점에서는 여러 remote와 브랜치일 뿐이며, fork·PR은 호스팅 서비스가 제공하는 협업 개념입니다.

제4부: 이력 통합과 정리

17. merge, rebase, squash 비교

merge

  • 분기와 통합 사실을 보존한다.
  • 기존 커밋을 다시 만들지 않는다.
  • 공유 이력에 안전하다.
  • 복잡한 프로젝트에서는 그래프가 풍부해질 수 있다.

rebase

  • 내 커밋의 기반을 새 기준점으로 옮긴다.
  • 커밋을 새로 만들므로 해시가 바뀐다.
  • 개인 작업 브랜치를 최신 main 위에 정리할 때 유용하다.
  • 이미 공유된 커밋을 rebase하면 동료의 기준과 어긋난다.
rebase 전
A---B---C  main
     \
      D---E  feature

rebase 후
A---B---C---D'---E'  feature

D와 E가 이동한 것이 아니라, 같은 변경을 기반 C 위에 적용한 새 커밋 D', E'가 만들어진 것입니다.

git switch feature
git fetch origin
git rebase origin/main

충돌 시:

git status
# 해결
git add <파일>
git rebase --continue
# 포기하고 원상복귀
git rebase --abort

경고: 공유 브랜치나 다른 사람이 기반으로 작업 중인 커밋은 합의 없이 rebase하지 마세요.

squash

여러 커밋을 하나의 커밋으로 합쳐 main에 넣습니다. 기능 브랜치의 세세한 시행착오보다 최종 변경 단위를 강조하고 싶을 때 적합합니다.

git switch main
git merge --squash feature/profile
git commit -m "feat: 프로필 편집 기능 추가"

선택 기준:

  • 실제 분기 기록과 개별 커밋을 보존: merge
  • 개인 브랜치의 선형 이력을 정리: rebase
  • 기능 전체를 main의 한 변경으로 표현: squash merge

정답은 하나가 아닙니다. 팀이 이력을 어떻게 읽고 되돌릴지에 따라 선택합니다.

18. interactive rebase

interactive rebase는 최근 개인 커밋의 순서, 메시지, 결합 방식을 정리합니다.

git rebase -i HEAD~4

편집 화면 예:

pick a111111 로그인 폼 추가
pick b222222 오타 수정
pick c333333 테스트 추가
pick d444444 다시 오타 수정

다음처럼 바꿀 수 있습니다.

pick a111111 로그인 폼 추가
fixup b222222 오타 수정
pick c333333 테스트 추가
fixup d444444 다시 오타 수정

주요 지시어:

  • pick: 그대로 사용
  • reword: 내용은 유지하고 메시지 수정
  • edit: 해당 커밋에서 멈춰 수정
  • squash: 앞 커밋과 합치고 메시지 편집
  • fixup: 앞 커밋과 합치고 현재 메시지는 버림
  • drop: 커밋 제거

안전 절차:

git status
git log --oneline -10
git branch backup-before-rebase
git rebase -i HEAD~4

잘못되면 진행 중에는 git rebase --abort, 완료 후에는 git reflog에서 이전 위치를 찾아 백업 브랜치를 만들 수 있습니다.

19. cherry-pick

cherry-pick은 다른 줄기의 특정 커밋이 만든 변경을 현재 브랜치에 새 커밋으로 적용합니다.

main:    A---B---C
hotfix:      \---H
release: A---B---R

H만 release에도 필요하다면:

git switch release
git cherry-pick <H의-해시>

사용 사례:

  • 긴급 수정 한 건을 여러 유지보수 브랜치에 적용
  • 잘못된 브랜치에 만든 커밋을 올바른 브랜치로 옮김
  • 큰 브랜치 전체가 아닌 검증된 변경 하나만 선택

주의점:

  • 같은 변경을 여러 번 cherry-pick하면 중복과 충돌 가능성이 커진다.
  • 브랜치 전체를 계속 동기화하는 도구로 쓰면 관계가 불명확해진다.
  • 충돌 시 해결 후 git cherry-pick --continue, 포기 시 --abort한다.

20. revert와 reset

둘은 목적이 완전히 다릅니다.

revert: 역사를 보존하며 취소 기록 추가

git revert <나쁜-커밋>

공유된 main에서 안전한 기본 선택입니다. 기존 커밋을 지우지 않고 그 효과를 반대로 적용한 새 커밋을 만듭니다.

reset: 브랜치 포인터를 과거로 이동

git reset --soft HEAD~1   # 커밋만 취소, 변경은 staged
git reset HEAD~1          # 커밋 취소, 변경은 unstaged
git reset --hard HEAD~1   # 커밋과 작업 변경을 버림
  • --soft: 커밋을 다시 구성하려 할 때
  • 기본 --mixed: 변경을 작업 디렉터리에 두고 스테이징을 다시 할 때
  • --hard: 작업 디렉터리와 스테이징 영역까지 대상 커밋에 맞출 때

위험: reset --hard는 커밋되지 않은 변경을 잃게 할 수 있습니다. 중요한 저장소에서는 먼저 git status, git diff, git log를 확인하고 백업 브랜치 또는 별도 패치를 만드세요.

git status
git diff
git log --oneline -10
git branch backup-before-reset
git reset --hard <대상>

공유 브랜치의 공개 커밋을 취소하려면 대체로 revert를 우선합니다.

21. stash와 임시 작업

stash는 아직 커밋하기 싫은 변경을 잠시 치워 깨끗한 작업 디렉터리를 만드는 기능입니다.

git stash push -m "로그인 폼 작업 중"
git stash list
git switch main
# 긴급 수정 후
git switch feature/login
git stash apply stash@{0}

apply는 적용 후 stash를 남기고, pop은 적용에 성공하면 목록에서 제거합니다. 초보자에게는 복구 여지가 있는 apply가 더 안전합니다.

추적하지 않는 파일까지 포함:

git stash push -u -m "새 파일 포함 임시 저장"

특정 stash를 독립 브랜치로 복구:

git stash branch recover-login stash@{0}

stash는 장기 보관소가 아닙니다. 공유되지 않고 맥락이 약하므로 오래 유지할 가치가 있는 작업은 명확한 WIP 커밋을 개인 브랜치에 남기는 편이 낫습니다.

22. tag와 릴리스

태그는 특정 커밋을 사람이 이해하기 쉬운 이름으로 고정합니다.

git tag -a v1.0.0 -m "첫 안정 릴리스"
git show v1.0.0
git push origin v1.0.0

annotated tag는 작성자, 시각, 메시지 등 메타데이터를 포함하므로 릴리스 표시에 적합합니다.

git tag -a v1.0.1 <커밋-해시> -m "보안 수정 릴리스"

태그를 옮기거나 삭제하면 이미 내려받은 사용자의 태그와 불일치할 수 있습니다. 릴리스 태그는 가능한 한 변경하지 말고, 잘못된 릴리스라면 새 버전을 만드는 정책이 이해하기 쉽습니다.

제5부: 복구와 진단

23. 안전 원칙

Git에서 사고가 났다고 느끼면 다음 순서를 지킵니다.

  1. 추가 명령을 연속해서 실행하지 않는다.
  2. git status를 읽는다.
  3. git log --oneline --graph --decorate --all을 본다.
  4. 작업 변경이 있다면 파일을 별도 폴더에 복사하거나 패치를 만든다.
  5. 현재 커밋에 안전 브랜치를 만든다.
  6. git reflog를 확인한다.
  7. 정확한 복구 목표를 정한 뒤 한 단계씩 실행한다.
git diff > ../working-tree-backup.patch
git diff --staged > ../staged-backup.patch
git branch backup-before-recovery
git reflog

“당황해서 hard reset”은 가장 피해야 할 행동입니다. 먼저 무엇이 커밋되어 있고 무엇이 아직 작업 디렉터리에만 있는지 구분해야 합니다.

24. reflog와 잃어버린 커밋 복구

브랜치나 HEAD가 이동한 기록은 reflog에서 찾을 수 있습니다.

git reflog

예:

9f9f9f9 HEAD@{0}: reset: moving to HEAD~2
7e7e7e7 HEAD@{1}: commit: 결제 검증 추가
6d6d6d6 HEAD@{2}: commit: 주문 테스트 추가

reset 전 커밋을 찾았다면 먼저 브랜치로 보호합니다.

git branch recovered-work 7e7e7e7
git show recovered-work

이후 필요한 방식으로 통합합니다.

git cherry-pick 7e7e7e7
# 또는 recovered-work 브랜치를 검토 후 merge

reflog는 영구 백업이 아니며 주로 로컬 기록입니다. 따라서 원격 백업과 의미 있는 브랜치·태그도 중요합니다.

25. detached HEAD와 삭제 브랜치

특정 커밋을 직접 확인하면 detached HEAD가 될 수 있습니다.

git switch --detach <커밋>

읽기만 하면 문제없습니다. 여기서 새 커밋을 만들었고 보존하고 싶다면 즉시 브랜치를 만듭니다.

git switch -c experiment-from-old-version

이미 다른 곳으로 이동했다면:

git reflog
git branch recovered-experiment <커밋-해시>

삭제한 브랜치도 커밋 객체가 즉시 사라지는 것은 아니므로 reflog에서 끝 커밋을 찾아 복원할 수 있습니다.

git reflog --all
git branch restored-feature <커밋-해시>

26. bisect로 버그 도입 커밋 찾기

커밋이 많을 때 하나씩 확인하지 않고 이진 탐색으로 최초의 나쁜 커밋을 찾습니다.

git bisect start
git bisect bad                 # 현재 버전은 버그 있음
git bisect good v1.2.0         # 이 태그에서는 정상

Git이 중간 커밋으로 이동하면 테스트 후 표시합니다.

npm test
git bisect good
# 또는
git bisect bad

찾기가 끝나면 반드시 원래 상태로 돌아갑니다.

git bisect reset

테스트 명령이 성공 시 0, 실패 시 비영(非零) 종료 코드를 반환한다면 자동화할 수 있습니다.

git bisect start HEAD v1.2.0
git bisect run npm test -- --runInBand
git bisect reset

bisect의 핵심은 “누가 잘못했는지 찾기”가 아니라 회귀 원인을 좁혀 수정 비용을 낮추는 것입니다.

27. 위험 명령과 복구 계획

27.1 git clean

추적되지 않은 파일을 삭제합니다. 이 파일은 Git 이력에 없으므로 복구가 특히 어렵습니다.

git clean -n     # 반드시 먼저 미리보기
git clean -i     # 가능하면 대화형 삭제
git clean -fd    # 파일·디렉터리 실제 삭제: 주의

27.2 강제 push

일반 강제 push는 원격 이력을 덮어쓸 수 있습니다.

git push --force

가능하면 다음을 사용합니다.

git fetch origin
git log --oneline --left-right origin/feature...feature
git push --force-with-lease

--force-with-lease는 내가 마지막으로 확인한 뒤 원격이 바뀌었다면 실패하여 타인의 새 커밋을 덮어쓸 위험을 낮춥니다. 그러나 위험이 0이 되는 것은 아닙니다.

안전 체크리스트:

  • 보호 브랜치인지 확인
  • 팀원에게 이력 재작성 예고
  • 원격 최신 상태 fetch
  • 로컬 백업 브랜치 생성
  • 덮어써질 커밋 확인
  • 가능하면 --force-with-lease
  • 사고 시 원격에 있던 커밋 해시나 동료 clone을 이용해 복구

27.3 전체 이력 재작성

비밀정보나 대용량 파일을 모든 과거 커밋에서 제거할 때 git filter-repo 같은 도구를 사용할 수 있습니다. 이는 모든 관련 커밋 해시를 바꾸고 기존 clone과의 관계를 깨뜨릴 수 있습니다.

최고 위험 경고: 실제 저장소에서는 저장소 관리자와 팀 전체의 명시적 합의, 자격증명 폐기, mirror 백업, 작업 중지 시간, 재복제 안내가 없으면 실행하지 마세요.

개념적 백업:

git clone --mirror <저장소-URL> backup-repository.git

비밀정보 유출에서는 이력 정리보다 키 폐기·재발급이 먼저입니다. Git 이력에서 지워도 이미 복제되거나 캐시된 비밀은 안전해지지 않습니다.

제6부: 고급 구조와 자동화

28. worktree

한 저장소의 여러 브랜치를 서로 다른 작업 디렉터리에서 동시에 열 수 있습니다.

상황: feature 작업 중인데 main에서 긴급 수정이 필요합니다. stash하고 브랜치를 계속 바꾸는 대신 새 worktree를 만듭니다.

git worktree add -b hotfix/payment ../app-hotfix main
cd ../app-hotfix
# 긴급 수정과 커밋

목록과 제거:

git worktree list
git worktree remove ../app-hotfix
git worktree prune

장점:

  • 빌드 결과와 의존성 디렉터리를 분리할 수 있다.
  • 두 브랜치를 에디터에서 동시에 비교할 수 있다.
  • 긴급 작업 때문에 현재 작업 상태를 치울 필요가 적다.

주의: 같은 브랜치를 일반적으로 두 worktree에서 동시에 checkout하지 못합니다. worktree 폴더를 운영체제 명령으로 무작정 삭제하기보다 git worktree remove를 사용합니다.

29. submodule

submodule은 한 저장소가 다른 저장소의 특정 커밋을 참조하게 합니다.

git submodule add https://example.com/team/shared-ui.git vendor/shared-ui
git commit -m "build: shared-ui 서브모듈 추가"

부모 저장소는 하위 저장소의 전체 내용을 직접 기록하는 대신 어느 커밋을 사용해야 하는지 기록합니다.

복제:

git clone --recurse-submodules <URL>
# 또는 이미 clone했다면
git submodule update --init --recursive

핵심 오해: 부모 저장소에서 submodule 포인터를 갱신한 것과 submodule 저장소에 그 커밋을 push한 것은 별개입니다. 팀원이 접근할 수 없는 커밋을 부모가 가리키면 빌드가 깨집니다.

submodule이 적합한 경우:

  • 독립적인 버전과 권한을 가진 컴포넌트
  • 부모가 하위 의존성의 정확한 커밋을 고정해야 함

대안:

  • 패키지 관리자
  • monorepo
  • subtree

운영 복잡성이 있으므로 “코드를 재사용하고 싶다”는 이유만으로 바로 선택하지 말고 릴리스·권한·빌드 모델을 검토합니다.

30. hooks

hook은 특정 Git 이벤트 전후에 실행되는 스크립트입니다. 로컬 hook은 보통 .git/hooks/에 있습니다.

예: 커밋 전 린트 실행

#!/usr/bin/env bash
npm run lint || exit 1

실행 권한이 필요한 환경:

chmod +x .git/hooks/pre-commit

주요 hook:

  • pre-commit: 커밋 생성 전 검사
  • commit-msg: 메시지 규칙 검사
  • pre-push: push 전에 테스트
  • post-merge: 병합 후 의존성 갱신 등

중요한 한계: .git/hooks의 로컬 파일은 일반적으로 저장소 커밋에 자동 포함되지 않습니다. 팀 공유가 필요하면 hook 관리 도구나 저장소 내 스크립트, CI를 사용해야 합니다.

hook은 개발자 피드백을 빠르게 만들지만, 건너뛸 수 있거나 환경 차이로 실패할 수 있습니다. 최종 품질 규칙은 서버 CI와 브랜치 보호 정책에서도 검증하는 것이 좋습니다.

31. Git LFS와 큰 파일

Git은 소스 코드처럼 작은 텍스트 파일의 버전 관리에 강합니다. 자주 바뀌는 대형 바이너리를 일반 Git 객체로 계속 커밋하면 저장소가 커지고 clone이 느려질 수 있습니다.

Git LFS는 저장소에는 포인터 파일을 기록하고 실제 대용량 콘텐츠는 별도 LFS 저장소에서 관리합니다.

git lfs install
git lfs track "*.psd"
git lfs track "*.zip"
git add .gitattributes
git add design/home.psd
git commit -m "design: 홈 화면 원본 추가"
git lfs ls-files

주의점:

  • 팀원과 CI 환경에도 Git LFS 지원이 필요하다.
  • 호스팅 서비스의 저장·전송 한도와 비용을 확인한다.
  • 이미 일반 Git 이력에 들어간 대형 파일을 LFS로 바꾸는 것은 이력 재작성이 될 수 있다.
  • 빌드 산출물은 LFS보다 릴리스 저장소나 아티팩트 저장소가 더 적합할 수 있다.

32. 플랫폼별 유의점

32.1 줄바꿈

Windows는 흔히 CRLF, Linux/macOS는 LF를 사용합니다. 줄바꿈 차이만으로 파일 전체가 바뀐 것처럼 보이지 않도록 .gitattributes로 프로젝트 정책을 명시할 수 있습니다.

* text=auto
*.sh text eol=lf
*.bat text eol=crlf

일반적인 개인 설정 예:

# Windows 작업 디렉터리는 CRLF, 저장소에는 LF
git config --global core.autocrlf true

# macOS/Linux에서는 입력 시 LF로 정규화
git config --global core.autocrlf input

팀의 .gitattributes가 개인 추측보다 우선되어야 합니다.

32.2 파일명 대소문자

Linux 파일시스템은 보통 대소문자를 구분하지만 Windows와 기본 macOS 환경은 그렇지 않은 경우가 많습니다. user.js와 User.js가 다른 파일로 인식되는 환경 차이 때문에 CI에서만 실패할 수 있습니다.

대소문자만 바꾸는 rename:

git mv --force user.js User.js

32.3 실행 권한

Linux/macOS의 스크립트 실행 비트가 Windows에서 잘 드러나지 않을 수 있습니다.

git update-index --chmod=+x scripts/deploy.sh

32.4 경로와 셸

Git 명령에서는 / 경로 구분자를 여러 플랫폼에서 사용할 수 있습니다.

git add src/components/Header.jsx

공백이 있는 경로는 따옴표로 묶습니다.

git add "docs/user guide.md"

Windows의 Git Bash, PowerShell, CMD는 인용·환경변수·스크립트 문법이 다릅니다. 문서의 Bash 예제에서 $(date ...) 같은 표현은 PowerShell에서 그대로 작동하지 않습니다. 플랫폼에 맞는 명령으로 바꾸거나 고정된 백업 브랜치 이름을 사용하세요.

git branch backup-before-reset

33. 협업 전략 선택

GitHub Flow

  • 항상 배포 가능한 main
  • 짧은 기능 브랜치
  • PR, 리뷰, 자동 테스트 후 병합
  • 웹 서비스와 소규모 팀에 이해하기 쉬움

Git Flow

  • main, develop, feature, release, hotfix 등 여러 장기·단기 브랜치
  • 명시적 릴리스 단계가 있는 제품에 맞을 수 있음
  • 브랜치 수와 병합 비용이 커질 수 있음

Trunk-Based Development

  • main 중심
  • 매우 짧은 브랜치 또는 직접 통합
  • 자동 테스트, 기능 플래그, 빠른 리뷰가 중요
  • “브랜치가 적다”보다 “작은 변경을 자주 안전하게 통합한다”가 핵심

선택 질문:

  • 얼마나 자주 배포하는가?
  • 여러 버전을 동시에 유지하는가?
  • 자동 테스트가 얼마나 신뢰할 수 있는가?
  • 코드 리뷰 대기 시간은 어느 정도인가?
  • 규제·승인 절차가 있는가?
  • 팀이 복잡한 이력 전략을 운영할 역량이 있는가?

도구보다 팀의 의사소통 규칙이 중요합니다. 병합 방식, 커밋 메시지, 브랜치 보호, 강제 push 금지 범위를 문서화하세요.

34. 보안과 인증

HTTPS와 SSH

  • HTTPS: 자격증명 관리자나 토큰을 통해 인증하기 편리
  • SSH: 키 기반 인증으로 반복 작업에 편리

SSH 키 생성 예:

ssh-keygen -t ed25519 -C "hong@example.com"

개인 키는 절대 공유하거나 커밋하지 않습니다. 공개 키만 호스팅 서비스에 등록합니다.

커밋 서명

서명은 커밋 작성자의 키와 연결된 검증 정보를 제공합니다. 하지만 서명됐다는 사실이 코드가 안전하거나 리뷰되었다는 뜻은 아닙니다.

비밀정보 예방

  • .env를 .gitignore에 추가
  • 예시는 .env.example에 키 이름만 기록
  • secret scanner와 pre-commit 검사 사용
  • CI 로그에 비밀이 출력되지 않도록 주의
  • 유출 시 즉시 폐기·회전

제7부: 종합 실습·오해·문제

35. 종합 프로젝트 실습

다음 실습은 로컬 저장소 두 개를 이용해 원격 협업을 흉내 냅니다. 실제 GitHub 계정 없이도 핵심 구조를 볼 수 있습니다.

35.1 중앙 원격 역할의 bare 저장소 만들기

mkdir git-course-lab
cd git-course-lab
git init --bare central.git

bare 저장소에는 일반 작업 디렉터리가 없으며 서버의 원격 저장소 역할을 흉내 내기 좋습니다.

35.2 개발자 A 저장소

git clone central.git alice-app
cd alice-app
git switch -c main
printf "# 메모 앱\n" > README.md
printf '{"name":"memo-app"}\n' > package.json
git add .
git commit -m "chore: 프로젝트 초기 구조 생성"
git push -u origin main

35.3 개발자 B 저장소

cd ..
git clone central.git bob-app
cd bob-app
git switch main

35.4 A가 기능 브랜치 작업

cd ../alice-app
git switch -c feature/add-note
mkdir -p src
printf "export function addNote(text) { return { text }; }\n" > src/note.js
git add src/note.js
git commit -m "feat: 메모 생성 함수 추가"
printf "\n## 기능\n- 메모 추가\n" >> README.md
git add README.md
git commit -m "docs: 메모 추가 기능 설명"
git push -u origin feature/add-note

35.5 리뷰를 흉내 내고 main에 병합

git switch main
git merge --no-ff feature/add-note -m "merge: 메모 추가 기능 통합"
git push origin main

--no-ff는 기능 브랜치의 통합 지점을 명시적으로 남깁니다. 실제 팀에서는 PR의 병합 정책을 따릅니다.

35.6 B가 원격 변경 관찰

cd ../bob-app
git fetch origin
git log --oneline --graph --decorate --all
git diff main...origin/main
git merge --ff-only origin/main

35.7 양쪽에서 충돌 만들기

B:

printf "# 팀 메모 애플리케이션\n" > README.md
git add README.md
git commit -m "docs: 프로젝트 제목 구체화"
git push origin main

A:

cd ../alice-app
printf "# 초간단 메모 앱\n" > README.md
git add README.md
git commit -m "docs: 프로젝트 제목 간결화"
git push origin main

A의 push는 원격에 B의 새 커밋이 있어 거절될 것입니다. 강제 push하지 말고:

git fetch origin
git log --oneline --left-right main...origin/main
git merge origin/main

충돌을 열어 두 의도를 조합한 제목을 작성합니다.

# 초간단 팀 메모 애플리케이션

그 후:

git add README.md
git commit
git push origin main

35.8 잘못된 커밋을 안전하게 되돌리기

printf "API_KEY=do-not-use-real-secrets\n" > demo.env
git add demo.env
git commit -m "chore: 잘못된 데모 설정 추가"
BAD_COMMIT=$(git rev-parse HEAD)
git revert "$BAD_COMMIT"

이 예시는 가짜 문자열만 사용합니다. 실제 비밀이 커밋되었다면 revert만으로 보안 문제가 해결되지 않으며 키를 폐기해야 합니다.

35.9 tag 만들기

git tag -a v0.1.0 -m "교육용 첫 릴리스"
git push origin v0.1.0
git log --oneline --graph --decorate --all

35.10 worktree로 긴급 수정

git worktree add -b hotfix/readme ../alice-hotfix main
cd ../alice-hotfix
printf "\n## 지원\n이슈를 등록해 주세요.\n" >> README.md
git add README.md
git commit -m "docs: 지원 안내 추가"

이 실습을 마친 뒤 다음을 말로 설명해 보세요.

  • origin/main과 main은 왜 다를 수 있는가?
  • push 거절은 왜 안전장치인가?
  • 충돌 해결이 단순히 최신 줄을 선택하는 문제가 아닌 이유는?
  • revert가 reset보다 공유 main에 적합한 이유는?

36. 흔한 오해

오해 1: git add는 파일을 저장한다

에디터의 저장은 작업 디렉터리를 바꾸고, git add는 현재 변경을 다음 커밋 후보로 복사합니다.

오해 2: commit하면 GitHub에 올라간다

commit은 로컬 기록입니다. 원격에는 push해야 전달됩니다.

오해 3: 브랜치는 폴더 전체의 복사본이다

브랜치는 커밋을 가리키는 가벼운 이름표입니다. 작업 디렉터리는 HEAD가 가리키는 스냅샷에 맞춰 바뀝니다.

오해 4: origin은 원격 서버 그 자체다

origin은 remote의 관례적 이름입니다. 다른 이름을 쓸 수 있고 여러 remote를 등록할 수도 있습니다.

오해 5: pull은 단순 다운로드다

pull은 보통 fetch 후 merge 또는 rebase까지 수행합니다. 자동 통합이 싫다면 fetch로 먼저 관찰하세요.

오해 6: 충돌은 누군가 실수했다는 뜻이다

서로 양립할 수 없는 변경이 있다는 뜻일 뿐입니다. 요구사항을 이해하는 사람이 최종 의도를 결정해야 합니다.

오해 7: 최신 파일을 고르면 항상 맞다

두 브랜치가 서로 다른 기능을 추가했다면 둘 다 살려야 할 수 있습니다. 시각보다 의미가 중요합니다.

오해 8: reset과 revert는 같은 취소다

reset은 참조를 이동하고, revert는 반대 변경을 새 커밋으로 남깁니다. 공유 이력에서는 revert가 일반적으로 안전합니다.

오해 9: rebase는 merge의 더 좋은 버전이다

둘은 이력 표현 방식이 다릅니다. rebase는 커밋을 다시 만들기 때문에 공유 이력에 위험할 수 있습니다.

오해 10: --force-with-lease는 완전히 안전하다

일반 force보다 안전하지만 이력 재작성 자체의 협업 비용과 실수 가능성은 남습니다.

오해 11: .gitignore에 넣으면 과거에서도 삭제된다

이미 커밋된 파일과 과거 이력에는 영향을 주지 않습니다.

오해 12: Git은 백업 시스템이다

분산 복제 덕분에 복원력이 있지만, 커밋하지 않은 파일, LFS 데이터, 데이터베이스, 외부 서비스 설정까지 자동 백업하지는 않습니다.

오해 13: 커밋은 완벽할 때만 해야 한다

커밋은 작고 논리적으로 검증 가능한 단위면 됩니다. 다만 공유 main에 넣기 전 팀의 품질 기준을 만족해야 합니다.

오해 14: 커밋 수가 적을수록 이력이 깨끗하다

서로 다른 의도를 한 거대한 커밋에 넣으면 리뷰와 되돌리기가 어려워집니다. 중요한 것은 수가 아니라 의미 있는 경계입니다.

38. 해설

  1. Git은 로컬 중심의 분산 버전 관리 도구입니다. GitHub는 Git 저장소 호스팅과 PR·이슈·리뷰 같은 협업 기능을 제공하는 서비스입니다.
  2. 작업 디렉터리는 재료를 손질하는 조리대, 스테이징 영역은 이번 접시에 담을 재료를 고른 쟁반, 커밋은 완성된 한 접시의 기록에 비유할 수 있습니다.
  3. git diff는 작업 디렉터리와 스테이징 영역, git diff --staged는 스테이징 영역과 HEAD를 비교합니다.
  4. 상태와 diff를 확인하고 git add A, staged diff 확인, commit 순서로 수행합니다.
  5. 보통 git status와 git diff입니다.
  6. 변경의 목적과 범위를 알려 주지 않아 리뷰·검색·복구에 도움이 되지 않기 때문입니다.
  7. .gitignore는 기본적으로 미추적 파일 선택을 제어하며 이미 index에서 추적하는 파일은 별도로 추적 해제해야 합니다.
  8. 브랜치에서 새 커밋을 만들면 브랜치 이름이 그 새 커밋을 가리키도록 이동하기 때문입니다.
  9. 현재 checkout한 브랜치 또는 커밋 위치를 나타냅니다.
  10. 마지막 fetch 시점에 갱신된 로컬의 원격 추적 참조이기 때문입니다.
  11. fetch는 원격 정보를 가져오지만 현재 브랜치에 통합하지 않습니다. pull은 보통 fetch 후 merge 또는 rebase까지 합니다.
  12. 먼저 fetch하고 원격에만 있는 커밋을 조사한 뒤 merge 또는 rebase 정책에 따라 통합해야 합니다.
  13. 아닙니다. PR은 GitHub 같은 호스팅 서비스의 협업 기능입니다.
  14. 병합 명령을 실행할 때 현재 checkout해 있던 브랜치 쪽 내용입니다.
  15. merge는 기존 커밋과 분기 관계를 보존하지만 rebase는 변경을 새 기반 위의 새 커밋으로 다시 만들기 때문입니다.
  16. 커밋 해시가 바뀌어 동료의 기존 이력과 다른 이력이 생기고 중복·충돌·강제 push가 필요해질 수 있기 때문입니다.
  17. 기능 브랜치의 시행착오 커밋보다 완성된 기능 하나를 main의 한 단위로 남기고 싶을 때입니다.
  18. 동일 변경이 여러 해시로 복제되고 중복 적용·충돌·출처 추적 문제가 커질 수 있습니다.
  19. 기존 공개 이력을 삭제하지 않고 반대 변경을 새 커밋으로 남기므로 동료 저장소와 관계를 깨뜨리지 않습니다.
  20. apply는 적용 후 stash를 남기고, pop은 성공적으로 적용한 stash를 제거합니다.
  21. 대개 git status입니다. 이어서 log, diff, reflog를 관찰합니다.
  22. git reflog입니다. 찾은 커밋에 우선 복구 브랜치를 만들어 보호합니다.
  23. 현재 위치에서 git switch -c <새-브랜치>로 이름을 붙입니다. 이미 떠났다면 reflog에서 해시를 찾아 branch를 만듭니다.
  24. git clean -n 또는 --dry-run으로 삭제 대상을 확인하고 필요한 파일을 별도 백업해야 합니다.
  25. 마지막 확인 이후 원격이 바뀌었으면 거절해 다른 사람의 새 커밋을 덮어쓸 위험을 낮추기 때문입니다.
  26. 정상임을 아는 과거 커밋과 문제가 있는 현재 커밋이 있고 각 중간 버전을 판정할 테스트가 있을 때 유용합니다.
  27. stash는 한 작업 디렉터리의 미완성 변경을 치웁니다. worktree는 별도 디렉터리에 다른 브랜치를 동시에 checkout합니다.
  28. submodule 저장소의 특정 커밋을 가리키는 참조입니다.
  29. 로컬 hook은 자동 배포·공유되지 않을 수 있고 사용자가 우회하거나 환경 차이로 실행되지 않을 수 있기 때문입니다. 서버 CI도 필요합니다.
  30. 노출된 키를 즉시 폐기하고 새 키로 회전합니다. 그 후 이력 정리와 영향 조사를 수행합니다.
  31. 개인 이력이라면 git rebase -i에서 해당 커밋을 reword하는 방법이 적합합니다. 먼저 백업 브랜치를 만들면 더 안전합니다.
  32. 올바른 브랜치에서 해당 커밋을 cherry-pick합니다. 잘못된 브랜치에서 제거할지는 공유 여부에 따라 개인 이력이면 reset, 공유 이력이면 revert를 검토합니다.
  33. 어느 줄이 더 최근인지가 아니라 제품 요구사항, 설정의 의미, 테스트 결과와 팀 결정을 근거로 해야 합니다.
  34. Git LFS, 파일 유형별 추적 정책, 호스팅 한도와 비용, 빌드 산출물의 별도 아티팩트 저장을 검토합니다.
  35. 현재를 bad, 정상인 과거 버전을 good으로 지정해 bisect를 시작하고 자동 테스트를 git bisect run으로 실행한 후 원인 커밋을 조사하고 git bisect reset으로 종료합니다.

39. 최종 핵심 요약

반드시 기억할 정신 모델

파일 편집
  ↓
작업 디렉터리
  ↓ git add: 다음 커밋에 넣을 변경 선택
스테이징 영역
  ↓ git commit: 의미 있는 스냅샷 기록
로컬 저장소
  ↓ git push: 원격에 참조 갱신 제안
원격 저장소

일상 안전 루틴

git status
git diff
git add -p
git diff --staged
git commit -m "변경의 목적을 설명하는 메시지"
git fetch origin
git log --oneline --graph --decorate --all
git push

통합 선택

  • 공개 이력을 보존하며 합치기: merge
  • 공유하지 않은 개인 커밋을 새 기반 위에 정리: rebase
  • 특정 커밋 하나만 가져오기: cherry-pick
  • 공개된 잘못된 변경을 새 커밋으로 취소: revert
  • 로컬 브랜치 포인터와 작업 상태를 재배치: reset — 옵션에 따라 위험

위기 대응

git status
git log --oneline --graph --decorate --all
git reflog

위험한 작업 전에는:

git diff > ../backup.patch
git branch backup-before-danger

마지막 조언

Git 실력은 명령어를 빨리 입력하는 능력이 아닙니다. 현재 상태를 관찰하고, 변경을 의미 단위로 나누고, 커밋 그래프가 어떻게 변할지 예측하고, 협업자에게 안전한 방식을 선택하는 능력입니다. 모르는 상황에서는 삭제나 강제 덮어쓰기보다 관찰, 백업, 새 브랜치를 먼저 선택하세요.
